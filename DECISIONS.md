# Decisions

*[Versión en español](DECISIONS.es.md)*

Here are the choices made along the project and a small reason for each. When a choice changed over time, only its latest form is kept.

| Date | Decision | Why |
|---|---|---|
| 2026-10-23 | Study DeiT-Small, with DeiT-Tiny as the smaller uncompressed alternative. | Understanding the model to be compressed and have something to compare it against. |
| 2026-10-23 | Every point is scored on ImageNet-1k val, ImageNet-V2 and ImageNet-R, with paired-bootstrap intervals on the same images. | One test set can hide how compression behaves under distribution shift, and small differences need a paired test. |
| 2026-10-23 | Only methods that need no training and have public code are replicated. | We can run them under one protocol; methods that retrain are listed but left out because we lack the compute or specialized kernel. |
| 2026-10-23 | Token-reduction methods are left off the chart. | They do not change the file size. |
| 2026-10-26 | Each published method runs with its authors' code and settings: the layers it quantizes, its grid shape and its number of calibration images. | The point on the chart should be as close to the authors' method as possible for accurate comparison. |
| 2026-10-26 | The calibration images are one training image per class, shuffled with seed 0 (`splits/calib_seed0.txt`), and a method that uses N images takes the first N. | Every method uses the same image set shuffled in the same way to represent as many classes as possible. |
| 2026-10-26 | Round-to-nearest stays on the chart as the reference. | It shows how much each method's search gains at each size. |
| 2026-10-30 | Each published method runs twice from its authors' code: as published, with weights and activations quantized at the bit widths its paper reports, and weights-only, with activations at full precision. Between methods, only the calibration images and the test sets change. | Most of the published ideas act on activations, so only the first run tests a method as its authors meant it, while the second is the one comparable with our own method, and the distance between the two shows how much of a method's loss comes from the activations. |
| 2026-10-30 | For a few methods, the authors' own random draw of calibration images is also run once. | Swapping in our calibration images is the one change that could handicap a method, and this measures its effect alone. |
| 2026-10-30 | Latency and memory at run time are measured for the formats with a real kernel on our RTX 4070: FP32, FP16, W8A8, DeiT-Tiny and the pruned models. | A smaller file is faster or lighter at run time only when a kernel computes with the compressed weights directly, and the distance between what the file size promises and what the GPU delivers is part of the answer. |
| 2026-10-30 | The W8A8 series takes the torchao point and every published method that reports 8 bits, run as published. | INT8 weights and activations are the one low-bit format our GPU computes with natively, so these points have a real kernel behind their latency. |
| 2026-10-30 | FLOPs, BOPs and the time to compress are reported for every point. | FLOPs change with pruning, BOPs also with bit width and stand in for hardware that computes in low bit widths natively, and the time a method takes to calibrate is part of what it costs. |
| 2026-11-03 | Pruning on the chart is GRAIL, the pruning stage of VBP and CORP, all without retraining. Methods that retrain stay as future work. | The protocol trains nothing, and fine-tuned pruning next to untrained quantization would make the comparison uneven. |
| 2026-11-03 | CORP is our reimplementation from its paper, with a relative ridge of 1e-3, and is labelled so. | We found no public code. Its DeiT-S numbers at 10 to 50 % come within about 1.4 points of the paper's local PDF, and the ridge value is ours because the paper does not print one. |
| 2026-11-03 | GRAIL runs twice, with the 128 images its paper states and with 4 000. | Its paper and its code disagree (its code uses 6 400), and 4 000 images add up to 4.6 points on val with Wanda selection. |
| 2026-11-03 | The calibration list grows to five rounds, 4 889 lines. Each round after the first 1 000 lines adds one more image per class, drawn and shuffled the same way, and every earlier line stays as it was. | Block reconstruction in APHQ-ViT and FIMA-Q uses 1 024 images, and CORP and VBP use 4 000, more than one per class. Appending leaves every shorter prefix, and so every earlier run, as it was. |
| 2026-11-03 | Pruned models are tested at low bits with round-to-nearest as the floor and FIMA-Q weights-only as the search, the search only on the models likely to land between 6 and 9 MB. | Pruning alone never beat an unpruned model of the same size or smaller. A FIMA-Q run takes about 47 minutes per point, so it goes where the curve has a gap. |
| 2026-11-03 | FIMA-Q also runs at W2 on unpruned DeiT-S, with the settings of its W3 config and only the weight bits changed, and is labelled as not a published setting. | The chart holds no unpruned DeiT-S between 6.19 and 8.78 MB, so the wins of pruning there had nothing fair to compete with. |
| 2026-11-03 | Sensitivity changes one unit at a time and keeps the rest in FP32. It reports KL from FP32, logit MSE and top-1 change on the first 2 000 calibration images and on every tenth val image. Quantization has 50 layers; pruning has each block's MLP and, for CORP, its Q and K. | The first set is the only one an allocation may look at, and the second checks that its ranking holds on images it did not see. |
| 2026-11-03 | Latency of pruned models is measured once per set of layer sizes, in a separate file, with dense FP16 timed again in the same session as the reference. | Latency depends on layer sizes and not on weight values, and timing runs from different sessions can differ by several percent. |
| 2026-11-04 | VBP's fine-tuning stays out and goes to future work. | It needs the full ImageNet training set, of which we hold 8 716 images, and about 5 hours per point, and the protocol trains nothing. |
| 2026-11-04 | APHQ-ViT's weights-only run now includes its MLP reconstruction, which replaces GELU with ReLU and retrains the MLPs on calibration images. The run without it stays on record as an ablation. | It is part of the published method and adds about 30 minutes. It trains weights, so the point is labelled, and its file needs ReLU to score. |
| 2026-11-04 | The curves on the main figure are monotone fits through our own real models, with the points shown and the published methods placed around them. A claim that one model beats another comes from paired comparisons between real models, never from the distance to a fit. | A smooth curve and a straight line through the same four unpruned models give opposite verdicts on the pruned points between 6.7 and 8.1 MB, so the fit alone cannot settle it. |
| 2026-11-04 | ERQ, I&S-ViT and FQ-ViT are left out. | They were optional and the date is close. FQ-ViT's 8-bit point is the one loss. |
| 2026-11-04 | The contribution is a measurement study of where DeiT-S loses accuracy when compressed after training and what the compression delivers. The ranking of fragile layers comes from MixFrag and our own sensitivity runs, and the allocator follows OBC, so neither is presented as new, and no separate depth test is run. | The deadline is close, and these questions already have published answers that our sensitivity runs agree with. |
| 2026-11-04 | Besides the weights-only curves, the chart gets points with weights and activations quantized: the published methods as published, FIMA-Q W8A8, our bits-only and combined models with 8-bit activations, and the pruned models stored as W8A8. They are measured down to 8-bit activations; below that, BOPs and memory are calculated and labelled so, and latency is not estimated. This extends the 2026-10-30 rows, and the main curves stay weights-only. | Activations do not change the file, but they decide memory traffic and arithmetic on real hardware, and 8 bits is the lowest activation width our GPU computes with natively. |
| 2026-11-04 | Which activations are fragile is tested on FIMA-Q at W3A3, with W4A4, W6A6 and W8A8 for comparison, and CORP is the pruning method for the candidates pushed until they break. The tests and the rule for calling a point fragile were written in `ABLATIONS.md` before any test ran, and the switch tests use FIMA-Q's checkpoints from after calibration. W1 is dropped. | FIMA-Q is the published quantizer that does best at low bits and gives no activation special treatment. Its finished checkpoints hold rounded weights and cannot return to FP32, which `ABLATIONS.md` explains. |
| 2026-11-04 | Compression order follows the Progressive Intensity Hypothesis (Kim et al., ICLR 2026): pruning first, then quantization. One short check at CORP joint 20 and 30 % with FIMA-Q W3 runs the other order. | The order already has a published answer, and the check only asks whether our pipeline's order costs anything in the range where the two curves meet. |
| 2026-11-04 | Latency is reported as measured, with the note that the available low-bit GPU kernels were not built for this architecture. There is no CPU test, no alignment of pruned widths to kernel sizes and no low-bit kernel timing of pruned models. This narrows the 2026-10-30 latency row. | Those timings say little about what low-bit hardware could deliver. Pruned FP16 timings need no special kernel and stay as measured. |
